# ثبت و مشاهده لاگ‌های بک‌اند

پیاده‌سازی: logging استاندارد Python/Django به همراه `django-log-viewer==1.1.8`؛ بدون جدول یا migration جدید و بدون سرویس خارجی. نسخه پکیج روی Python 3.9.6 / Django 3.2.7 محلی نصب و تست شده است. وابستگی دیگری ارتقا داده نشد.

## محل مشاهده

پس از ورود با **مدیر کل فعال (superuser)**، لینک «مشاهده و دانلود لاگ‌های بک‌اند» در صفحه اصلی Django Admin دیده می‌شود. مسیر داخلی بک‌اند:

```text
/admin/project-logs/
```

با پراکسی فعلی پروژه، آدرس عمومی معمولاً چنین است:

```text
https://doctor.gosheshenava.com/api-backend/admin/project-logs/
```

اگر ادمین را مستقیماً از پورت بک‌اند باز می‌کنید، همین مسیر `/admin/project-logs/` را به آدرس همان بک‌اند اضافه کنید. برای نمایش از پراکسی، آدرس static و هدایت صفحه ورود ادمین نیز باید در پیکربندی فعلی Nginx درست مسیردهی شوند. این تغییر تنظیمات Nginx را دست نمی‌زند.

پنل، فهرست فایل‌ها، جست‌وجوی رکوردهای بارگذاری‌شده، صفحه‌بندی و دانلود را با پکیج انجام می‌دهد. پنل دیتابیس قابل جست‌وجوی نامحدود نیست؛ هر بار حداکثر ۲۰۰ رکورد از فایل بارگذاری می‌شود. جست‌وجوی همه آرشیوها را با ابزارهای فایل انجام دهید. دسترسی staff عادی کافی نیست؛ پاسخ‌ها cache نمی‌شوند. فایل‌های خارج از الگوی تعیین‌شده، مسیرهای traversal و symlinkها قابل خواندن نیستند.

## فایل و اطلاعات ثبت‌شده

فایل پیش‌فرض: `BASE_DIR/logs/project.log`، روی سرور فعلی `/root/myprojectdir/backend/logs/project.log`. این پوشه وارد Git، media یا static نمی‌شود. پوشه جدید با مجوز 0700 و فایل جدید با 0600 ایجاد می‌شوند؛ Gunicorn و worker باید به همین پوشه دسترسی داشته باشند. اگر با کاربران سیستم‌عامل متفاوت اجرا می‌شوند، مالکیت/گروه مجاز را اپراتور هماهنگ کند.

هر پاسخ، شامل 2xx و 4xx و 5xx، یک رکورد `request_finished` دارد: زمان UTC، سطح، متد، قالب مسیر، کد وضعیت، زمان پردازش، شناسه داخلی کاربر در صورت دسترسی و `request_id`. همین شناسه در هدر `X-Request-ID` به فرانت برمی‌گردد و برای درخواست‌های CORS نیز expose شده است. شناسه ورودی کاربر قابل اعتماد تلقی نمی‌شود و سرور UUID جدید تولید می‌کند.

خطاهای مدیریت‌نشده Django علاوه بر خلاصه درخواست، نوع exception و فریم‌های traceback (نام فایل، شماره خط و نام تابع) دارند. خطاهای DRF مثل ValidationError با حفظ پاسخ فعلی، نوع exception را به رکورد اضافه می‌کنند. شکست ارسال OTP/پیامک، خطای اتصال پی‌استار و نتیجه نامعلوم ساخت تماس رزروشده نیز در سرویس‌ها ثبت می‌شوند. پاسخ‌های تجاری که در کد با `Response(..., status=400)` ساخته می‌شوند حداقل مسیر، وضعیت و شناسه پیگیری دارند؛ اگر exception ایجاد نشده باشد، traceback ندارند.

**حریم خصوصی:** بدنه درخواست/پاسخ، query string، headers، توکن، OTP، username/شماره تماس، متغیرهای محلی، خط سورس و پیام خام exception یا logger ذخیره نمی‌شوند. مسیر از الگوی resolver گرفته می‌شود؛ مقدار پارامترهای URL ثبت نمی‌شود. پیام خام یک exception ممکن است حاوی URL سرویس و کلید یا اطلاعات مراجع باشد؛ بنابراین به‌جای آن نوع و محل خطا نگهداری می‌شود. متن آزاد `logger.info/error` نیز عمداً حذف می‌شود. این سیاست باعث می‌شود لاگ برای یافتن محل خطا مفید باشد، اما شامل تمام داده‌های ورودی یا جزئیات شخصی نباشد. قرارداد APIهای قدیمی تغییر نکرده است.

این قالب برای فایل و کنسول/journal اعمال می‌شود. خطای نوشتن فایل، پاسخ درخواست را خراب نمی‌کند؛ پیام ثابت در stderr ثبت می‌شود و خروجی پاک‌سازی‌شده کنسول همچنان موجود است. `django.request` ممکن است علاوه بر خلاصه middleware، یک رکورد exception/وضعیت هم بدهد؛ با `request_id` یکسان قابل ارتباط‌اند. خطاهای worker خارج از درخواست، request_id ندارند.

نمونه بررسی روی سرور:

```bash
sudo tail -n 100 /root/myprojectdir/backend/logs/project.log
sudo grep -F 'REQUEST_UUID' /root/myprojectdir/backend/logs/project.log*
sudo journalctl -u gunicorn -n 100 --no-pager
```

کلیدهای پیگیری را از Network مرورگر، هدر پاسخ `X-Request-ID` بردارید. خطای 502 تولیدشده در Nginx/CDN پیش از رسیدن درخواست به Django در این فایل ثبت نمی‌شود؛ لاگ Nginx/CDN باید جداگانه بررسی شود. فایل‌های access/error مستقل Nginx یا تنظیمات خود Gunicorn به این پکیج متصل نشده‌اند.

## نصب در سرور و چرخش فایل

پکیج در `reqFinal.txt` ثبت شده است. پس از انتقال کد، داخل venv سرور:

```bash
python -m pip install --no-deps django-log-viewer==1.1.8
python -m pip check
python manage.py collectstatic --noinput
```

اگر دسترسی PyPI سرور محدود است، از همان mirror تأییدشده سرور استفاده کنید. هیچ متغیر جدید .env یا migration جدید برای این قابلیت لازم نیست. بعد از نصب و انتقال کد، Gunicorn و worker باید طبق روال استقرار پروژه مجدداً کد جدید را بارگذاری کنند؛ در این تغییر روی سرور restart انجام نشده است.

چرخش فایل را با نمونه `deploy/project-logs.logrotate.example` آماده کنید. قبل از نصب، `SERVICE_USER` و `SERVICE_GROUP` را با کاربر/گروه واقعی سرویس جایگزین کنید. نمونه، چرخش روزانه یا با اندازه بیش از ۱۰ مگابایت در زمان اجرای logrotate و نگهداری ۱۴ آرشیو را تنظیم می‌کند. این سقف لحظه‌ای حجم نیست؛ وابسته به زمان‌بندی اجرای logrotate است. فشرده‌سازی خاموش است تا پنل بتواند آرشیوها را بخواند.

`WatchedFileHandler` با جابه‌جایی فایل توسط logrotate، در اولین رکورد بعدی فایل جدید را باز می‌کند؛ برخلاف چرخش داخلی هر process، Gunicorn و worker بر سر rename فایل رقابت نمی‌کنند. نمونه به‌صورت خودکار روی سیستم نصب نشده است؛ بدون logrotate فایل خودبه‌خود کوچک یا پاک نمی‌شود.

## تست

تنظیمات تست از `config.settings` و `.env` استفاده نمی‌کنند و دیتابیس و پوشه موقت مستقل دارند:

```bash
.venv/bin/python manage.py test config.test_logging --settings=config.logging_test_settings --noinput
.venv/bin/python manage.py test --settings=config.logging_test_settings --noinput
```

تست‌ها پاسخ‌های 200/400/404/500، حفظ قرارداد پاسخ، traceback بدون اطلاعات حساس، استقلال request_id درخواست‌های همزمان، شکست دیسک، چرخش خارجی فایل، سطح دسترسی پنل/JSON/دانلود، فایل‌های static محلی و منع خواندن فایل غیرمجاز یا symlink را پوشش می‌دهند.

نتیجه اجرای محلی در ۲۰۲۶-۱۱-۱۸: مجموعه کامل ۱۸۱ تست بدون شکست (۸ تست نیازمند قفل واقعی دیتابیس روی SQLite skip شدند)، ۱۴ تست اختصاصی لاگ‌گیری موفق، pip check موفق و بررسی migration بدون تغییر. همین مجموعه با تنظیمات رگرسیون قبلی نیز اجرا و موفق شد. هیچ تستی به سرویس واقعی یا دیتابیس سرور متصل نشد.
