# وضعیت فعلی رزرو نوبت و آزمون‌های مشاور

تاریخ بررسی: 2026-11-16. این سند برای تعیین اصلاحات بعدی نوشته شده و توصیف کد فعلی است، نه تأیید صحت عملکرد یا طراحی پیشنهادی قطعی. هیچ تغییر اجرایی، عملیات دیتابیس، تماس، پیامک یا پرداخت واقعی انجام نشده است.

## ۱. دامنه و تفکیک دو جریان

چهار صفحه خواسته‌شده به دو زیرسامانه مستقل تعلق دارند. واژه Visit در نام‌ها به معنی یکسان بودن مدل یا فرایند نیست.

| فایل فرانت | مسیر Vue | نقش |
| --- | --- | --- |
| `src/views/exam/Visit.vue` | `/exam/visit/:id/:slug` | شرکت کاربر در آزمون، پرداخت از کیف پول و ثبت پاسخ سؤال‌ها |
| `src/views/exam/UsersExam.vue` | `/users/exam/visit/:id/:slug/:userId` | مشاهده پاسخ‌های شرکت‌کننده و ثبت نتیجه مشاور |
| `src/views/visit/Index.vue` | `/visits/:id/:fullname` | ثبت درخواست نوبت با انتخاب تاریخ/ساعت و شماره تماس |
| `src/views/visit/Show.vue` | `/visits/show/:id` | فهرست درخواست‌های مشاور و تأیید نوبت |

همه این routeها `meta.loginRequired=true` دارند؛ این کنترل فرانت جای مجوز بک‌اند را نمی‌گیرد. ساختار Vue از Options API، Vue Router و Vuex استفاده می‌کند. بک‌اند در requirements فعلی Django 3.2.7 و DRF 3.12.4 دارد.

در دو مسیر آزمون، `:id` شناسه `CreateExam` است. در دو مسیر نوبت، `:id` شناسه `Author` است. `:userId` صفحه UsersExam شناسه User شرکت‌کننده است. `:slug` برای واکشی جداگانه آزمون استفاده می‌شود؛ فرانت تطابق نتیجه slug با id را بررسی نمی‌کند.

تمام مسیرهای API این سند نسبت به ریشه Django هستند؛ با baseURL فعلی، مرورگر پیشوند `/api-backend/` را نیز دارد. `author-shift` نام موجود API برای رکورد نوبت است، نه جدول جداگانه اسلات‌های آزاد مشاور.

## ۲. مدل‌های مرتبط

منبع: [api/models.py](../api/models.py).

| مدل | رابطه‌ها و داده‌های مهم |
| --- | --- |
| `Author` | مشخصات مشاور، User مرتبط و ساعت‌های کاری `oneDay` تا `sevenDay` |
| `CreateExam` | تعریف آزمون؛ `authorId → Author`، `userId → User`، نام، slug یکتا، amount و status شامل d/p/e |
| `QuestionsExam` | سؤال متعلق به CreateExam؛ متن، تصویر، نوع گزینه‌ای/تشریحی و چهار گزینه |
| `VisitExam` | شرکت در آزمون؛ `userId`, `examId`, `active` با معنی پرداخت‌شده و `authorAnswer` حداکثر ۲۵۰ کاراکتر |
| `AnswerVisitedExam` | پاسخ یک User به یک سؤال در آزمون؛ `userId`, `examId`, `questionId`, `answer` حداکثر ۲۵۰ کاراکتر |
| `AuthorVisit` | نوبت؛ `AuthorId → Author`، `AuthorUserId → User مشاور`، `userId → User متقاضی`، number، visitTime، active و autoDial |
| `call.Number` | شماره‌های جایگزین کاربر؛ برای انتخاب شماره هنگام رزرو، نه رابطه مستقیم با AuthorVisit |

تفاوت کلیدی `active`: در `VisitExam` یعنی پرداخت آزمون، در `AuthorVisit` یعنی تأیید نوبت توسط مشاور. این دو وضعیت نباید یکی تلقی شوند.

در مدل‌های شرکت/پاسخ آزمون و نوبت، قید یکتایی برای جلوگیری از ثبت تکراری شرکت در آزمون، پاسخ یک سؤال یا اشغال هم‌زمان یک زمان دیده نشد. پاسخ سؤال مستقیماً به VisitExam وصل نیست؛ اتصال منطقی آن از ترکیب User و exam است.

`AuthorVisit.number` رشته‌ای با حداکثر ۱۰ کاراکتر است؛ کپی شماره انتخاب‌شده است، نه ForeignKey به Number. هیچ مبلغ، مدت جلسه یا وضعیت پرداخت در AuthorVisit تعریف نشده است. `active=False` و `autoDial=False` پیش‌فرض‌اند.

## ۳. جریان آزمون در exam/Visit.vue

### بارگذاری

1. `GET question/?examId=:id`: دریافت اولین صفحه سؤال‌ها در `results`؛ ظرفیت صفحه سؤال‌ها در بک‌اند ۲۰۰ است.
2. `GET visit/exam/?examId=:id`: دریافت شرکت‌های کاربر جاری؛ اولین نتیجه در `myExam` قرار می‌گیرد. اگر active دقیقاً true باشد، نمایش سؤال‌ها فعال می‌شود.
3. `GET exam/?slug=:slug`: اولین نتیجه به‌عنوان `exam` انتخاب می‌شود.
4. `POST answer/question/visit/exam` با `{examId}`: دریافت آرایه پاسخ‌های کاربر فعلی و افزودن `answer` به سؤال‌های متناظر در state.

مرحله‌های ۲ تا ۴ پس از دریافت سؤال‌ها شروع می‌شوند ولی نتیجه همدیگر را انتظار نمی‌کشند.

### شرکت، پرداخت و پاسخ

- `joinToExam()`: دریافت User جاری و `POST create/visit/exam/` با `{examId, userId}`؛ رکورد VisitExam ساخته می‌شود و پیش‌فرض پرداخت‌نشده است.
- `payJoinedExam()`: `POST payment-exam/` با `{examId: :id, questionId: myExam.id}`. نام questionId در این endpoint گمراه‌کننده است؛ اینجا شناسه **VisitExam** است، نه QuestionsExam.
- `sendAnswer(questionId)`: `POST answer/visit/new/` با `{examId, questionId, answer}`؛ در این endpoint، questionId واقعاً شناسه سؤال است.
- انتخاب گزینه یا تایپ متن با `document.querySelector` و تغییر مستقیم کلاس‌ها و مقدار textarea کنترل می‌شود؛ هر سؤال جداگانه ثبت می‌شود، نه یک ارسال نهاییِ تمام آزمون.
- بعد از ثبت پاسخ، سؤال به‌صورت پایدار در state به answered تبدیل نمی‌شود؛ امکان ارسال دوباره وجود دارد.
- وقتی `myExam.authorAnswer !== null` باشد، فرم پاسخ جدید در UI مخفی می‌شود. این محدودیت UI را نباید کنترل قطعی بک‌اند فرض کرد.

### APIهای آزمون

منابع: [api/urls.py](../api/urls.py)، [api/views.py](../api/views.py)، [api/serializers.py](../api/serializers.py)، [config/urls.py](../config/urls.py).

| API | کلاس/serializer و رفتار فعلی |
| --- | --- |
| `GET exam/?slug=…` | `CreateExamViewSet` / `CreateExamSerializer`؛ حذف پیش‌نویس‌ها با `exclude(status='d')`؛ فیلتر اختیاری slug و authorId |
| `GET question/?examId=…` | `QuestionsExamViewSet` / `QuestionsExamSerializer`؛ سؤال‌های exam انتخابی، نزولی id، صفحه ۲۰۰ |
| `POST create/visit/exam/` | `CreateVisitExamViewSet` / `CreateVisitExamSerializer`؛ serializer همه فیلدهای VisitExam را دارد، انتساب اجباری user در perform_create دیده نشد |
| `GET visit/exam/?examId=…` | `VisitExamViewSet` / `VisitExamSerializer`؛ queryset محدود به کاربر جاری، examId تو در تو serialize می‌شود |
| `POST answer/question/visit/exam` | `AnswerQuestionsViewSet`؛ پاسخ‌های User جاری و exam درخواست‌شده؛ پاسخ آرایه است، نه صفحه‌بندی |
| `POST answer/visit/new/` | `AnswerVisitedExamViewSetNew`؛ وجود VisitExam فعال برای User جاری و exam را بررسی می‌کند، سپس AnswerVisitedExam جدید می‌سازد |
| `POST payment-exam/` | `payment.views.PaymentExamViewSet`؛ کسر کیف پول و فعال کردن VisitExam؛ توضیح مالی در بخش بعد |

endpointهای سفارشی نمایش/ثبت پاسخ آزمون مطابق URLconf بدون اسلش یا با اسلش متفاوت‌اند؛ هنگام اصلاح مسیرها نباید اسلش را کورکورانه به همه اضافه کرد.

## ۴. پرداخت آزمون

منبع: [payment/views.py: PaymentExamViewSet](../payment/views.py).

- `CreateExam.amount` در این مسیر تومان فرض شده و در بک‌اند برای کسر کیف پول در ۱۰ ضرب می‌شود.
- پرداخت مستقیماً از `User.amount` است؛ این endpoint لینک درگاه Paystar تولید نمی‌کند. افزایش کیف پول مسیر جداگانه دارد.
- VisitExam با `id=request.data['questionId']` و قیمت با examId جداگانه بارگذاری می‌شوند.
- در همین متد کنترل صریح تطابق VisitExam با exam انتخابی، مالکیت آن برای پرداخت‌کننده یا پرداخت‌نشده بودن آن دیده نشد.
- عملیات قفل رکورد/transaction.atomic و محافظ پرداخت مجدد در این متد دیده نشد. فراخوانی تکراری می‌تواند مجدداً مبلغ را کم کند.
- رکورد پرداخت اختصاصی آزمون یا Transaction در همین متد ساخته نمی‌شود؛ active و موجودی تغییر می‌کنند.
- پاسخ موفق شامل `amount` یعنی **مانده کیف پول** است، نه مبلغ پرداخت یا سهم مشاور.

اختلاف‌های UI:

1. فرانت `store.amount >= exam.amount` را بررسی می‌کند، اما بک‌اند `exam.amount * 10` را لازم می‌داند؛ کنترل اولیه واحد یکسانی ندارد.
2. فرانت فقط اگر `response.data.amount` truthy باشد `active=true` می‌کند؛ پرداخت موفقی که مانده را صفر کند در UI فعال نمی‌شود تا داده دوباره بارگذاری شود.
3. بلوک پرداخت به truthy بودن `store.amount` وابسته است؛ برای موجودی صفر، حتی پیام افزایش موجودی/مسیر پرداخت رایگان هم نیازمند بررسی است.
4. state موجودی Vuex در `payJoinedExam()` با مانده جدید همگام نمی‌شود.

## ۵. جریان پاسخ مشاور در exam/UsersExam.vue

1. دریافت User جاری از auth و دریافت `userauthor/?userId=…`؛ اولین Author انتخاب و id آن برای مسیر بازگشت ذخیره می‌شود.
2. دریافت سؤال‌های `question/?examId=:id` و آزمون با `exam/?slug=:slug`.
3. `POST answer/question/visit/exam/new` با `{examId, userId}` برای دریافت پاسخ‌های کاربر داخل URL.
4. نمایش پاسخ هر سؤال و یک textarea برای نتیجه کلی مشاور.
5. `POST author/answer/to/visit/new/` با `{userId, examId, answer}`؛ سپس بازگشت به `/exam/<Author.id>`.

| API | رفتار فعلی بک‌اند |
| --- | --- |
| `POST answer/question/visit/exam/new` | `AnswerQuestionsViewSetNew`؛ پاسخ‌ها را بر اساس userId ورودی و examId برمی‌گرداند؛ تطبیق مشاور جاری با مالک آزمون دیده نشد |
| `POST author/answer/to/visit/new/` | `AuthorAnswerToVisitedExamViewSetNew`؛ VisitExam فعالِ userId/examId را می‌گیرد، اگر authorAnswer برابر None باشد نتیجه را ذخیره می‌کند؛ در غیر این صورت ۲۰۰ با `is answered` می‌دهد |
| `GET users/exam/?authorId=…` | مسیر پشتیبان لیست شرکت‌کننده‌ها در exam/Index؛ فقط شرکت‌های active آزمون‌های authorId ورودی را فیلتر می‌کند، محدودسازی به مشاور نشست در queryset دیده نشد |

ایراد قطعی در ترکیب پاسخ‌ها: حلقه بیرونی روی پاسخ‌ها و حلقه درونی روی سؤال‌هاست؛ در **هر بار** حلقه بیرونی، answer همه سؤال‌ها به «پاسخ داده نشده» بازنشانی می‌شود. در پایان معمولاً فقط پاسخ منطبق با آخرین پاسخ آرایه باقی می‌ماند. باید مقدار اولیه یک بار تعیین و سپس پاسخ‌ها نگاشت شوند؛ در این بررسی اصلاح نشده است.

UI فقط وجود متن را کنترل می‌کند، نه سقف ۲۵۰ کاراکتر. برای `is answered` هم به‌دلیل پاسخ HTTP 200 بدون تفکیک نتیجه، به صفحه قبل برمی‌گردد. نتیجه قبلی مشاور در این صفحه بارگذاری نمی‌شود.

## ۶. جریان ثبت نوبت در visit/Index.vue

ورودی این صفحه لینک‌های پروفایل مشاور در `components/Profile.vue` است. رزرو نوبت مستقل از شرکت در آزمون است.

1. دریافت User جاری؛ شماره پیش‌فرض `username` کاربر است.
2. `GET author-shift-list/?authorId=<Author.id>&myDate=7`: نمایش نوبت‌های ثبت‌شده مشاور با برچسب تأییدشده/درانتظار.
3. `GET numbers/`: دریافت شماره‌های جایگزین User برای انتخاب.
4. مودال `usersExamList` تاریخ/ساعت و شماره را می‌گیرد. نام مودال تاریخی است و اینجا آزمون ایجاد نمی‌کند.
5. DatePicker مقدار `YYYY-MM-DD HH:mm` می‌سازد و تاریخ جلالی را فقط برای نمایش نشان می‌دهد. timezone صریح در رشته ارسالی نیست؛ تنظیمات بک‌اند `Asia/Tehran` و `USE_TZ=True` است.
6. `getVisit()` فقط null نبودن زمان و شماره را کنترل و مودال را پیش از نتیجه شبکه می‌بندد.
7. `GET author/:id/` برای یافتن User مشاور.
8. `POST user-register-shift-using-author/` با این payload:

```text
AuthorId:     شناسه Author در URL
AuthorUserId: شناسه User مشاور از author/:id/
userId:       شناسه User واردشده
number:       شماره اصلی یا جایگزین انتخابی
visitTime:    تاریخ/ساعت انتخابی
```

9. در پاسخ ۲۰۱، فهرست هفت‌روزه مجدداً خوانده و پیام موفقیت نمایش داده می‌شود.

این صفحه اسلات آزاد از ساعات کاری Author تولید نمی‌کند؛ کاربر زمان دلخواه وارد می‌کند. تطبیق با `oneDay…sevenDay`، آینده بودن زمان، ظرفیت، مدت جلسه، تداخل و هم‌زمانی ثبت در کد این مسیر دیده نشد. برای رزرو در این مسیر مبلغی کسر نمی‌شود و job تماس ایجاد نمی‌شود.

## ۷. APIهای نوبت و تأیید

| API | کلاس/serializer | رفتار واقعی |
| --- | --- | --- |
| `POST user-register-shift-using-author/` | `UserRegisterShiftUsingAuthorViewSet` / `VisitSerializer` | ساخت AuthorVisit با شناسه‌های payload؛ active در serializer نیست، پیش‌فرض False؛ autoDial قابل ارسال است |
| `GET user-register-shift-using-author/` | همان ViewSet | queryset فقط نوبت‌های User جاری؛ وجود پارامتر active، صرف‌نظر از مقدارش، فیلتر True اعمال می‌کند |
| `GET author-shift-list/?authorId=…&myDate=7` | `AuthorShiftListViewSet` / `AuthorVisitListSerializer` | فهرست نوبت‌های Author انتخابی؛ فقط visitTime، active و jpublish؛ نه شماره و هویت متقاضی، نه id |
| `GET author-shift/?authorId=…` | `AuthorShiftViewSet` / `AuthorVisitSerializer` | فهرست نوبت‌های `AuthorUserId=request.user.id`؛ پارامتر authorId اصلاً استفاده نمی‌شود |
| `PATCH author-shift/<AuthorVisit.id>/` | همان ViewSet | UI فقط `{active: true}` می‌فرستد؛ queryset محدود به User مشاور و مجوز شیء `IsAuthorUserIdOrReadOnly` دارد |
| `POST SendAdminMsgToUser/` | `ticket.views.SendAdminMsgToUserViewSet` | ارسال پیامک با ورودی username؛ مجوز فقط `IsSuperUser` |

`VisitSerializer` شامل AuthorId، AuthorUserId، userId، number، visitTime، autoDial و jpublish است. `AuthorVisitSerializer` شامل id، userId عددی، visitTime، autoDial، active و jpublish است و شماره تماس را در پاسخ این صفحه ارائه نمی‌کند.

### مانع فعلی فیلتر تاریخ

در `api/views.py` ابتدا `import datetime` و سپس `from datetime import datetime, timedelta` وجود دارد؛ نام datetime در نهایت کلاس است، نه ماژول. درحالی‌که `AuthorShiftListViewSet` از `datetime.date.today()` و `datetime.timedelta(...)` استفاده می‌کند.

در نتیجه شاخه myDate، که Index همیشه با ۷ می‌فرستد، مستعد AttributeError و پاسخ ۵۰۰ است. این ناسازگاری import در یک بررسی مستقل Python، بدون بارگذاری Django یا تماس با سرور، تأیید شد. شاخه active در AuthorShiftViewSet هم همان الگو را دارد؛ درخواست فعلی Show بدون active وارد آن شاخه نمی‌شود.

حتی پس از رفع import، بازه فعلی از نیمه‌شب امروز تا نیمه‌شب هفت روز بعد است، نه «اکنون تا ۱۶۸ ساعت بعد». زمان‌های گذشته امروز را هم می‌پذیرد و بخش عمده روز انتهایی را در بر نمی‌گیرد. بررسی مرز روز، timezone و DST/تبدیل تاریخ لازم است.

### روند Show.vue

- لینک‌های داشبورد و Navbar به `/visits/show/<Author.id>` می‌روند، اما API مالکیت را با User نشست تعیین می‌کند، نه id موجود در URL.
- صفحه همه نوبت‌های خود مشاور را می‌گیرد؛ فیلتر تاریخ یا authorId اعمال نمی‌شود مگر پارامترهای پشتیبانی‌شده دیگری اضافه شود.
- انتخاب نوبتِ غیرفعال، آن را در `item` می‌گذارد و مودال تأیید را باز می‌کند.
- `getVisit()` رکورد را active کرده و لیست را refresh می‌کند؛ پس از refresh پیام تأیید نمایش داده می‌شود.
- بعد درخواست پیامک با `{bodyId: 85105, username: item.userId, param: ''}` فرستاده می‌شود.
- شماره‌ها و callNumber در mounted بارگذاری می‌شوند، اما در فرم تأیید استفاده یا به PATCH ارسال نمی‌شوند.

پیامک دو مشکل مستقل دارد: مشاور عادی برای endpoint ادمین مجوز ندارد؛ و `item.userId` یک شناسه عددی دیتابیس است، نه شماره موبایل مورد انتظار username. حتی اگر مجوز ادمین باشد، مقصد باید جداگانه بررسی شود. شکست پیامک، active شدن نوبت را rollback نمی‌کند و UI پیش از پیامک موفقیت تأیید را نشان داده است.

هیچ‌یک از این دو صفحه `call_create/` یا زمان‌بندی `createCallAtTime` را فراخوانی نمی‌کنند. وجود autoDial به‌تنهایی worker یا تماس خودکار نمی‌سازد. جزئیات شماره‌های جایگزین در [سند شماره‌ها](user-phone-numbers.md) آمده است.

## ۸. دسترسی و اعتبارسنجی: موارد لازم برای اصلاح

این بخش تحلیل کد است، نه اثبات بهره‌برداری روی سرور. `IsUserIdOrReadOnly` و `IsAuthorUserIdOrReadOnly` در وضعیت فعلی فقط `has_object_permission` دارند. کنترل شیء در create/list و APIView سفارشی به‌صورت خودکار مانند retrieve/update اجرا نمی‌شود. loginRequired فرانت نیز از فراخوانی مستقیم API جلوگیری نمی‌کند.

| اولویت | مشاهده |
| --- | --- |
| بالا | API خواندن پاسخ کاربر دیگر و ثبت نتیجه مشاور، مالکیت آزمون برای مشاور جاری را صریح بررسی نمی‌کنند؛ داده آزمون می‌تواند حساس باشد |
| بالا | پرداخت، VisitExam را با id ورودی مستقل از exam قیمت‌گذاری‌شده می‌گیرد؛ تعلق شرکت، آزمون و پرداخت‌کننده کنترل صریح ندارد |
| بالا | تکرار پرداخت، درخواست هم‌زمان و ذخیره ناقص بدون atomic/قفل در مسیر پرداخت آزمون کنترل نشده‌اند |
| بالا | userId و شناسه مشاور در ساخت نوبت/شرکت از payload پذیرفته می‌شوند؛ انتساب اجباری و تطبیق رابطه‌ها در سرور دیده نشد |
| بالا | تعلق questionId به examId در ثبت پاسخ و یکتایی پاسخ/شرکت تضمین نشده؛ `.get()` روی چند شرکت فعال نیز به خطا می‌خورد |
| عملکرد | برخورد import تاریخ، دریافت فهرست هفت‌روزه نوبت را مختل می‌کند |
| عملکرد | حلقه UsersExam پاسخ‌های قبلی را بازنشانی می‌کند |
| مالی/UI | واحد مقایسه مبلغ و شرط مانده صفر با بک‌اند یکسان نیست |
| عملکرد | پیامک تأیید از فرانت به endpoint ادمین با شناسه به‌جای شماره ارسال می‌شود |
| کیفیت | شماره نوبت بدون بررسی تعلق/OTP و بدون وابستگی FK ثبت می‌شود؛ رزرو تکراری یا گذشته منع اختصاصی ندارد |

کنترل فعال‌بودن شرکت در ثبت پاسخ وجود دارد، ولی بسته بودن پاسخ‌گویی پس از نتیجه مشاور در همان endpoint کنترل صریح ندارد. ModelViewSetها علاوه بر متدهای مصرف‌شده در UI، متدهای دیگری نیز ارائه می‌کنند؛ امنیت نباید فقط بر مبنای درخواست‌های همین چهار صفحه ارزیابی شود.

## ۹. تصمیم‌هایی که پیش از پیاده‌سازی لازم است

1. نوبت صرفاً درخواست زمان دلخواه است یا باید اسلات واقعی از تقویم/ساعات کاری انتخاب شود؟ مدت، ظرفیت و فاصله جلسات چیست؟
2. چه کسی حق ثبت، مشاهده، تأیید، رد، جابه‌جایی و لغو دارد؟ آیا مهلت و علت لغو لازم است؟
3. رزرو هزینه دارد؟ چه زمان از کیف پول کسر و در صورت لغو چگونه بازگردانده شود؟ این تصمیم مستقل از پرداخت آزمون است.
4. تأیید نوبت باید پیامک، یادآوری یا تماس خودکار بسازد؟ مقصد شماره اصلی است یا شماره انتخابیِ تأییدشده؟
5. یک کاربر چند بار می‌تواند در یک آزمون شرکت کند؟ پاسخ‌ها قابل ویرایش‌اند؟ پایان آزمون و پایان مهلت چگونه تعریف می‌شود؟
6. مشاور کدام شرکت‌کننده‌ها را می‌بیند و آیا نتیجه یک بار ثبت می‌شود یا نسخه‌بندی/ویرایش مجاز است؟
7. واحد مبلغ API و UI چیست و پرداخت موفق/تکراری/ناموفق چه قرارداد پاسخ مشترکی دارد؟
8. برای کاربر دارای چند Author، کدام رکورد و تقویم مبنای کار است؟ نمایش و اعتبارسنجی شناسه User و Author باید صریح باشد.

## ۱۰. چک‌لیست تست برای مرحله اصلاح

- جداسازی متقاضی/مشاور/ادمین/ناشناس و جلوگیری از خواندن پاسخ یا نوشتن نتیجه آزمون شخص دیگر.
- ثبت نوبت با User یا مشاور ناسازگار، شماره خارج از حساب، تاریخ گذشته، زمان خارج ساعت کاری و دو درخواست هم‌زمان.
- فهرست هفت روزه، مرز نیمه‌شب، تاریخ جلالی/میلادی، timezone و فهرست خالی/چندصفحه‌ای.
- تأیید فقط توسط مشاور مالک؛ پیامک موفق/ناموفق/تکراری و حفظ وضعیت مستقل تأیید.
- تطبیق شناسه‌های آزمون، سؤال، شرکت و پرداخت‌کننده؛ پرداخت تکراری و هم‌زمان، موجودی ناکافی و موجودی دقیقاً برابر هزینه.
- شرکت تکراری و سؤال با پاسخ تکراری، چند پاسخ نمایش‌داده‌شده، سؤال تشریحی/گزینه‌ای با گزینه‌های خالی و طول بیشتر از ۲۵۰.
- شکست شبکه در هر مرحله؛ پایان درست loading و جلوگیری از پیام موفقیت کاذب.

## ۱۱. حدود بررسی و تغییرات این مرحله

چهار صفحه، routeها، ورودی‌های لینک، مدل‌ها، serializerها، مجوزها و APIهای مرتبط بررسی شدند. برای این جریان‌ها تست اختصاصی مرتبط در جستجوی فایل‌های تست فعلی پیدا نشد؛ این به معنی پوشش صفر تمام وابستگی‌های عمومی نیست.

این مرحله فقط مستندات است. تست یکپارچه روی Django، مرورگر و دیتابیس اجرا نشد؛ فقط ناسازگاری import تاریخ مستقل از پروژه بررسی شد. هیچ task، پیامک، نوبت، شرکت در آزمون یا پرداختی روی سرور ایجاد یا اصلاح نشد. اصلاحات اجرایی، migration و تست رگرسیون پس از تصمیم مالک پروژه انجام می‌شوند.
