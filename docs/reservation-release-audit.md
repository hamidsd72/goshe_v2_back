تاریخ: ۲۰۲۶-۱۱-۱۷ — شاخه بررسی در هر دو مخزن: `feature/reservation-release-audit`.

مبنای Git بک‌اند `7855106` و فرانت `4256fdc`، به همراه تغییرات موجود در working tree و index بود. تغییرات از قبل stage‌شده حفظ شدند. تغییر مستقل ترتیب نمایش نظرات در `api/views.py` نیز حفظ شد؛ این فایل در این بررسی ویرایش نشد. Commit، push، استقرار یا اجرای migration روی سرور انجام نشد.

## نتیجه

مجموعه خودکار موجود پروژه و تست‌های جدید موفق‌اند. این نتیجه آمادگی کد را در محیط تست تأیید می‌کند؛ اتصال واقعی پیامک، تماس، درگاه، Nginx و worker سرور در این بررسی تست نشده است.

| بررسی | نتیجه |
| --- | --- |
| کشف و اجرای تمام تست‌های بک‌اند روی SQLite جداگانه | ۱۶۷ تست، بدون شکست؛ ۸ تست قفل دیتابیس skip شدند |
| تمام تست‌های بک‌اند روی MariaDB/InnoDB موقت | ۱۶۷ تست، بدون شکست و بدون skip؛ شامل ۵ تست رقابت رزرو و ۳ تست رقابت تسویه |
| تمام تست‌های فرانت در Docker | ۹۸ تست، بدون شکست |

محیط بک‌اند: Python 3.9.6، Django 3.2.7 و DRF 3.12.4. فرانت Vue 3 با Node 18 در Docker ساخته شد. اجرای همین تست‌ها روی Python 3.8 سرور انجام نشده است. MariaDB روی پورت loopback `33317` با فضای ذخیره‌سازی موقت tmpfs بود و پس از پایان حذف شد؛ به دیتابیس واقعی متصل نشدیم. migrationهای ذخیره‌شده، از جمله `api/0028_reservation_credit`، در دیتابیس تست از ابتدا اجرا شدند.

هش build نهایی: `88e110eb1c90ce7a`، فایل برنامه `js/app.feadf7cf.js`. هش با هر build بعدی ممکن است تغییر کند. چهار هشدار build مربوط به Bootstrap/autoprefixer و اندازه bundle هستند؛ خطای کامپایل وجود ندارد. هشدار قدیمی بودن داده Browserslist نیز وجود دارد؛ هیچ وابستگی ارتقا داده نشد.

## اصلاحات حاصل از بازبینی

۱. پس از پاسخ موفق ثبت رزرو، خطای `sessionStorage.removeItem` می‌توانست کاربر را با پیام ناموفق روبه‌رو کند، در حالی که رزرو و برداشت انجام شده بود. پاک‌سازی حافظه مرورگر اکنون نتیجه موفق ثبت‌شده در سرور را تغییر نمی‌دهد. تست ابتدا شکست خورد و پس از اصلاح پاس شد.

۲. پاسخ دیرهنگام ساخت تماس می‌توانست رزروی را که اپراتور اعتبارش را برگردانده بود به `in_call` برگرداند. اکنون وضعیت نهایی و دفتر اعتبار حفظ می‌شوند؛ شناسه دریافتی برای پیگیری ذخیره و `failure_code=provider_response_after_refund` ثبت می‌شود. اپراتور باید این تعارض را با سوابق سرویس تماس بررسی کند؛ هیچ استرداد یا تماس مجدد خودکاری انجام نمی‌شود.

۳. اگر در حین انتظار پاسخ سرویس، اپراتور شناسه معتبر دیگری را ثبت کرده باشد، پاسخ دیرهنگام آن را بازنویسی نمی‌کند. `failure_code=provider_id_mismatch` ثبت می‌شود. تست این حالت نیز پیش از اصلاح شکست خورد و پس از آن پاس شد.

این اصلاحات schema یا migration جدید ندارند و قرارداد APIهای قدیمی حساب/پروفایل/پیام را تغییر نمی‌دهند.

## سناریوهای بررسی‌شده

- زمان آزاد از فردا، ساعات کاری مشاور، مدت‌های ۱۰/۳۰/۶۰ دقیقه، هم‌پوشانی و پروفایل‌های تکراری یک مشاور.
- قیمت محاسبه‌شده در سرور، کنترل تغییر تعرفه، تبدیل تومان به ریال و عدم برداشت با موجودی ناکافی.
- پرداخت کل مبلغ رزرو، تأیید سروری، برگشت به همان فرم، UUID ثابت و جلوگیری از شارژ/رزرو دوباره در retry.
- لغو پرداخت بدون شارژ کیف پول؛ پرشدن نوبت هنگام پرداخت با باقی ماندن تمام مبلغ پرداختی در کیف پول.
- مالکیت شماره انتخابی و جداسازی فهرست رزروها؛ حذف شماره طرف مقابل از پاسخ‌های مخصوص رزرو؛ نمایش نام کاربر برای مشاور.
- لغو توسط مشاور، استرداد یک‌باره، حذف جاب تماس و پترن پیامک لغو.
- پردازش واقعی Taskهای دیتابیس با runner کتابخانه؛ جداسازی صف `reservations`، اجرا نشدن تماس پیش از موعد و پردازش پیامک‌ها.
- تماس فقط با اعتبار و نرخ snapshot رزرو، تماس دیرهنگام/طرف مشغول، callback زودرس و تکراری، نتیجه نامعلوم provider و بازیابی دستی.
- رقابت واقعی دو کاربر برای یک بازه، برداشت هم‌زمان از یک کیف پول، لغو هم‌زمان، دو worker و callbackهای هم‌زمان روی InnoDB.
- تست‌های موجود ورود/OTP، درگاه، حسابداری و تسویه مشاور، گزارش‌ها، ادمین و شماره‌های جایگزین.

## تکرار تست‌ها

فرمان‌ها از پوشه بک‌اند، با تنظیمات تست مستقل از `.env`:

```bash
.venv/bin/python manage.py test --settings=api.reservation_regression_test_settings --noinput
.venv/bin/python manage.py makemigrations --check --dry-run --settings=api.reservation_regression_test_settings
.venv/bin/python -m pip check
```

برای اثبات قفل‌های دیتابیس، ابتدا فقط یک MariaDB موقت محلی مشابه محیط شرح‌داده‌شده بسازید و سپس:

```bash
.venv/bin/python manage.py test --settings=api.reservation_release_test_settings --noinput
```

این تنظیمات فقط به `127.0.0.1:33317` و دیتابیس `test_goshe_reservations_qa` مربوط‌اند. برای استفاده روی دیتابیس سرور طراحی نشده‌اند.

از پوشه فرانت:

```bash
docker compose run --rm frontend yarn test:unit
docker compose run --rm frontend yarn eslint --no-fix src/views/visit/Index.vue src/views/visit/Show.vue src/views/PaystarResult.vue src/utils/reservations.cjs
docker compose run --rm frontend yarn build
```

## پیش از فعال‌سازی عمومی روی سرور

طبق [مستند اجرایی رزرو](reserved-consultations.md)، اعمال migration موجود `0028` و migrationهای `background_task` باید بررسی و توسط اپراتور تأیید شود. اینکه این migrationها قبلاً در سرور اعمال شده‌اند در این بررسی معلوم نشده است. worker باید دائماً صف `reservations` را پردازش کند؛ نیاز به سرویس Celery یا Redis جدید وجود ندارد.

بک‌اند و خروجی جدید فرانت با هم منتشر شوند. پس از استقرار، یک رزرو کنترل‌شده با حساب‌های آزمایشی و مبلغ کم، شامل پیامک هر دو طرف، ساخت تماس در موعد، callback احرازشده و برگشت اعتبار مصرف‌نشده بررسی شود. یک لغو توسط مشاور هم باید حذف جاب، استرداد و پیامک پترن 589593 را تأیید کند. تست‌های این گزارش سرویس‌های خارجی را mock کرده‌اند و ارسال پیامک، تماس یا پرداخت واقعی انجام نشده است.
